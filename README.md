# GDPval diagnostic evaluation

**Omissions and form, not arithmetic.** A diagnostic evaluation of Claude Opus 5.5 and
GPT-6.1-sol on ten GDPval v2 tasks, one run each, graded against the public GDPval v2 rubrics with
code graders (deterministic checks), an LLM judge and human review, followed by author review.
After review, Opus 5.5 passes 7 of 10 tasks and GPT-6.1-sol 3 of 10 (31 and 26 of 35 critical
requirements); the author confirmed 40 failed rubric items, in 4 categories.

- **None of the 40 confirmed failures is a wrong calculation.** The failures (failed rubric items)
  are content left out (25), a different label or form (11), and one rounding approach that breaks
  an accounting rule (4).
- **Only GPT-6.1-sol missed things the prompt asked for.** Each failure is tagged by whether the
  model was told: in the prompt; rubric only (GDPval's grading key expects it, the prompt doesn't
  say it); or the additions rule (ours, set before the runs). 12 of GPT-6.1-sol's 30 failures are
  in the prompt, such as store subtotals, and cost it 2 tasks. All 10 of Opus 5.5's are rubric
  only or the additions rule (report section 7.5).
- **Rubric grading needs a human pass.** Of the 100 graded fails the author reviewed, chosen
  where a verdict could change (78) or a model failure was suspected (22), 67 (67%) were grader false fails; in one task a grader false pass
  hid the only failure. 8 of the 10 task failures (3 Opus 5.5, 7 GPT-6.1-sol) turn only on rubric-only wording or detail, or
  the additions rule.

## Architecture overview

| Module | Responsibility |
|---|---|
| `harness/launcher.py` | Trusted host process: configuration and image pre-flight, credential names (never values), budget reservation and settlement through the ledger, the single Task / single EvalLog / single sample contract, run provenance and the run ↔ ledger binding. `--dry-run` performs every check without calling a provider; `--real-run` is the only paid path. |
| `harness/task.py`, `harness/samples.py`, `harness/tools.py` | The Inspect Task: frozen system prompt, four tools (`bash`, `python`, `view_image`, `render_document`), docker sandbox with no network, per-task input allowlist verified by hash. Nothing from `private/`, `preregistration.md` or the grader enters the sandbox. |
| `harness/collect.py` | Collects `/output/final/` from the sandbox onto the host with fail-closed validation and writes the authoritative `run_outcome.json`. Collected files are never modified afterwards. |
| `harness/budget.py` | The one authority for cost: reservations, settlements (exact, estimated, held), stops, manual reconciliations; append-only JSON ledger with a persistent `ledger_id`. `harness/ledger_admin.py` is the minimal manual-reconciliation command. |
| `grading/run_grading.py` | Offline grading of one saved run: binds run directory, Inspect log and task id, reads rubric / reference / prompt from host paths, runs `grade_run`, optionally the judged pass behind the judge gate, and writes the provenance record. |
| `grading/grade.py`, `grading/extract.py`, `grading/checks_1137e2bb.py` | Deterministic grading: outcome gate and log join, extraction on copies (with the LibreOffice recalculation in the trusted image), the task-specific pipeline that produces PASS / FAIL / cannot_assess per rubric item with locatable evidence and error attribution. |
| `grading/judge.py` | Judge units (task requirement, criterion, independent reference, deliverable excerpt), the provider adapter with structured call records and a write-ahead call log, response parsing. |
| `grading/review.py` | Human-review materials: deliverable and criterion first, the judge verdicts sealed in a separate file, the independent-judgment template never overwritten. |
| `grading/costs.py` | Cost records per run from ledger settlements. |

## Evaluation workflow

generation (`launcher --real-run`, one Task, one sample, k = 1) → collection (`run_outcome.json`, deliverables under `runs_root/<uuid>/final/`, `artifact_manifest.json`) → deterministic grading (`run_grading`, judge items pending) → human review from the sealed materials → judged pass (`run_grading --judge`, one provider call per judge-only criterion) → cost reconciliation (`ledger_admin`). Every paid step is gated: explicit scope restatement, audit metadata, budget reservation, no open reservation or hold on the ledger, and for a judge pass the run's ledger binding.

**Run classes.** Every execution belongs to one run class with its own root, ledger, Inspect logs, launcher and batch records and run inventory under `~/turing-eval-runs/<label>/` (`--run-label`, config `batches`): `dev` (one Gemini Flash sample per formal task, opened only after that task's Grader v0 is committed and tagged), `validation` (a second, independently generated Gemini Flash sample per task, sealed until the validation checkpoint), `compat` (one sample of each candidate on a GDPval task outside the formal ten; provider, tool, artifact and accounting behaviour only, never a capability result) and `formal` (10 tasks x 2 candidates after `freeze-v1`). The launcher refuses a root or ledger whose path does not carry the label or carries another class, a model the class does not allow, and a task outside the class's task set. Graders are developed gold-first: the expert deliverables are the anchor, seeded corruptions and layout transformations derived from them carry declared verdict transitions (`grading/gold_variants_1137e2bb.py`, `grading/gold_variants_7d7fc9a7.py`; records under `grading/validation/<task_id>/`). The shared grading engine (`grading/engine/`: cell reading and classification, verdict assembly and attribution, header mapping, sheet and month helpers, money quantization, the workbook gate) is extracted only where a second task demonstrated the need; each task keeps a thin specification (`grading/checks_<task8>.py`) with its own version.

## Execution commands

Dry run (no provider call; every check, the reservation logic and a voided reservation; the class's root and ledger must sit under a directory named after the label):

```
.venv/bin/python -m harness.launcher --dry-run --run-label dev --runs-root ~/turing-eval-runs/dev/runs --ledger ~/turing-eval-runs/dev/ledger.json     --task-id 1137e2bb-bdf9-4876-b572-f29b7de5e595 --model google/gemini-3.8-flash --estimate-usd 1.00
```

Paid generation of one unit (example only; requires the batch authorization recorded in `docs/status.md`, a credential in `.env` read by the launcher, and an environment that is not in mock mode):

```
.venv/bin/python -m harness.launcher --real-run --run-label <label> --runs-root ~/turing-eval-runs/<label>/runs --ledger ~/turing-eval-runs/<label>/ledger.json     --task-id <task_id> --model <provider/model> --estimate-usd <usd>     --confirm '<task_id>|<provider/model>|<usd>' --authorized-by '<name>' --authorization-ref '<status.md entry>'
```

A whole batch (`harness/batch.py`: every task of the class's task set, one model, sequentially through the launcher's gates; one authorization restated once with `--confirm-batch`; a task with a completed sample in the class inventory is skipped unless `--allow-repeat`; the batch stops at the first refusal, exception, stop or hold and never retries a unit):

```
.venv/bin/python -m harness.batch --run-label dev --model google/gemini-3.8-flash --runs-root ~/turing-eval-runs/dev/runs --ledger ~/turing-eval-runs/dev/ledger.json --dry-run
.venv/bin/python -m harness.batch --run-label dev --model google/gemini-3.8-flash --runs-root ~/turing-eval-runs/dev/runs --ledger ~/turing-eval-runs/dev/ledger.json     --real-run --confirm-batch 'dev|google/gemini-3.8-flash|10|1.00' --authorized-by '<name>' --authorization-ref '<status.md entry>'
```

Several run classes in parallel (`harness/scheduler.py`): one detached scheduler owns every paid launch of a plan, starts one unit at a time per class (each a one-task `harness.batch` invocation under `caffeinate -i` in its own session, so an interrupted terminal never stops it), keeps at most the configured number of paid units across classes (`config.concurrency.cross_class`), and applies the gate of `harness/unit_gate.py` after every unit (run outcome, collection and manifest consistency, structural file checks, settlement; for the development model also the tool-error-loop rule of `harness/run_metadata.py`, which reads counts only, and the two-limit rule). Files `stop_new` and `cap_override` in its state directory stop new launches or fix the cap; in-flight units are never terminated:

```
.venv/bin/python -m harness.scheduler --plan <plan.json> --dry-plan
```

Offline deterministic grading of a saved run (no provider call):

```
.venv/bin/python -m grading.run_grading --host-dir /abs/runs/<uuid> --eval-log /abs/runs/inspect_logs/<unit>/<log>.eval     --task-id <task_id> --out-dir /abs/grading/<uuid> --ledger /abs/ledger.json --unit-id '<generation unit id>'
```

Judged pass (paid; example only): add `--judge --judge-model <provider/model> --judge-estimate-usd <usd> --confirm-judge '<uuid>|<provider/model>|<usd>' --authorized-by '<name>' --authorization-ref '<ref>'`; a second judged pass of the same run needs `--rejudge`.

Manual reconciliation of a unit whose cost is unknown or held: `.venv/bin/python -m harness.ledger_admin resolve --ledger /abs/ledger.json --unit-id <unit> --resolution settled_amount --amount-usd <verified> --basis '<evidence>' --by '<name>'` (or `--resolution unresolvable`, which records the investigation and releases nothing); `... status --ledger /abs/ledger.json [--run-uuid <uuid>]` shows open reservations, holds and resolutions.

## Grading interpretation

Each rubric item is graded `pass`, `fail` or `cannot_assess` from evidence that names a file, sheet, cell or paragraph. A confirmed violation of the item's own text gives FAIL even when another input could not be assessed; an unreliable required input without a confirmed violation gives `cannot_assess`; every required comparison must be completed before a PASS. Attribution separates model-caused outcomes (`model_caused`, `model_caused_missing`, `model_caused_corrupt`) from grader-side ones (`grader_extraction`, `grader_caused_recalculation`, `grader_caused_extraction`) and `unknown`; judge-only items carry `error_class` `provider_error`, `judge_parse_error` or `not_attempted` when they could not be judged. Critical criteria (3 to 5 per task, listed in `preregistration.md`) fail when any of their items fails and are `not_confirmed` while items are pending or unassessable (the page calls this "undecided"). The rules and every adjudication are in `preregistration.md`.

## Grading pass versioning

`grade_run` appends one results record and one set of grade rows per pass and never overwrites: a deterministic-only pass (`pass_kind: deterministic_only`, judge items `pending_judge`) and later judged passes (`deterministic_plus_judge`, `supersedes_pass` naming the previous pass). `judge_completeness` is `complete`, `partial` (a provider error, parse error or not-attempted criterion) or `none`; a judge unit whose write-ahead log holds a started event without a terminal event is UNKNOWN. A report uses exactly one pass per model run: `grading.grade.select_pass` (with the run's persisted judge attempts from the ledger and the write-ahead logs, as `grading.run_grading.report_selection` assembles them) returns the latest judged pass with its basis and warnings; a partial latest pass is selected and flagged, never hidden behind an older complete one; when the latest judge attempt is UNKNOWN, open or held and produced no pass, the selection is `blocked` (no current pass, history kept) until it is reconciled. The selection fails closed: `report_selection` resolves the run's `ledger_binding.json` and opens the bound ledger itself, and is `blocked` when the binding is missing, names another run, or a supplied ledger is not the bound one; `selected_grades` requires the loaded attempt history and returns `blocked` with no rows without it; `select_pass` called without attempts is historical inspection (`authoritative: false`), never a report input; `authoritative_selection` is the statistics entry (selection plus the selected pass's rows, none while blocked). Two passes of one run are never two samples.

## Budget and safety

Each run class has its own ledger created from `config.batches.<label>` (ceiling as a start gate, allowed models, task set, per-model reservation forecasts, an optional per-sample Inspect cost limit for the non-formal classes); grading and reconciliation open an existing ledger with the ceiling and label it was created with and never decide a ceiling. Every paid unit is claimed atomically on the ledger before it starts (`BudgetLedger.reserve(claim=True)`: inside one lock, no other open reservation, the unit not already claimed, no stop condition) and settled from the provider-reported usage afterwards. A unit whose cost is not fully known - a model call without reported usage, an exception after calls were made, a judge batch with a missing or uncertain usage - is settled at the larger of the priced known part and the reservation, flagged `estimated`, and puts a persistent hold on further paid starts until a human reconciles it (`ledger_admin resolve` with the verified amount; `unresolvable` releases nothing). Known usage is recovered from durable evidence before such a settlement, bound to the execution: for generation, only Inspect logs in the execution's own log directory (`inspect_logs/<unit>/`) whose eval task and model match the unit, each (eval id, sample, epoch) counted once; a log that cannot be attributed is excluded and the settlement is flagged `attribution_uncertain`; for judge calls, the judge write-ahead log. What cannot be recovered stays unknown and is never counted as zero. A judge batch stops sending requests after the first call whose usage cannot be accounted (remaining criteria `not_attempted`). Open reservations of unknown outcome, UNKNOWN judge calls, holds, recorded stops (two engineering failures of one class, a unit above twice its estimate, the class ceiling) all refuse new paid starts and survive restarts because they are ledger events; a unit that was claimed and never settled is never re-run until reconciled. Cost records read the ledger's effective settlement (manual reconciliations applied), never a raw event. The reservation, the per-sample cost limit and the class ceiling are harness controls, not caps on the provider's bill; every pre-run cost figure is a forecast until reconciled with the account.

## Reproducibility

Private inputs that are not tracked: `data/inputs/<task_id>/` (task inputs), `data/prompts/`, `private/rubric/`, `private/gold/`, `private/checks/recalc/` (independent recalculations), the dataset parquet, and `.env` (credentials, read only by the launcher). Versions recorded with every run and grading pass: the code commit (`git rev-parse HEAD`, with a dirty flag), `config.json` sha256, the system prompt sha256 (checked against the config at launch), the sandbox image id and platform, the grader version (`<engine_version>+<task_grader_version>`: the shared engine `grading.grade.ENGINE_VERSION` and each task specification's `VERSION`, both checked against `config.grading` at grading, plus the full git commit of the grading code in every pass), the judge id. Tests run through `harness/tests/run_isolated.sh` (minimal environment, external working directory, `INSPECT_DISABLE_MODEL_API=1`, mockllm); the unit suites are `harness/tests/test_*_unit.py`, `harness/tests/test_launcher_regressions.py`, `harness/tests/test_generation_config.py`, `grading/tests/test_layout_regressions.py`, `grading/tests/test_gold_1137e2bb.py` and `grading/tests/test_gold_7d7fc9a7.py` (gold anchor, values-only twin, declared corruption and layout catalogs; `GOLD_RECALC_DOCKER=1` adds the LibreOffice path) and `grading/tests/test_grading_chain.py`; the mock integration regressions are `harness/tests/regress_*.py`, `grading/tests/regress_grading_cli.py` (which produces a fresh run through the real Inspect + docker + mockllm path) and `grading/tests/regress_recalc_docker.py`.

## Limitations

- **Sample.** 10 tasks, one run each: all 5 GDPval Order Clerks tasks plus 5 selected
  accounting and IT tasks. Counts are descriptive, not a model ranking.
- **Graders.** Grader false passes were checked only in the 20-item blind audit (1 in 18
  audited passes). The LLM judge's held-out validation (3/3) held only passing cases, so its
  ability to catch failures is untested.
- **Author choices.** The author chose the 35 critical requirements (fixed before the runs) and
  rated severity (after review).
- **Review.** One author, not a domain expert, about 3 hours; 42 rubric items left (cannot
  assess), 96 outside critical requirements not reviewed.
- **Rule dependence.** One pre-registered rule (additions listed line by line) decides 2 failed
  critical requirements per model.
- **Failure sources.** Tagged after the runs from the task prompts (Claude's draft, reviewed by
  the author); they change no verdict. 12 are borderline cases, each decided by the author and
  listed in report section 7.5.
- **Cost.** $30.06 for the 20 evaluation runs, generation and judging; $88.33 across all paid
  work, including development and validation runs. Generation alone: Opus 5.5 $14.90, GPT-6.1-sol $3.08, at the same
  'high' effort label.

Details and the full list of known limitations: `report/REPORT.md` section 8.2.

## Rebuilding the data from a clean clone

The repository tracks the records that identify the data (`data/dataset_revision.json`,
`data/selected_tasks.json`, `data/download_verification.json`, `data/manifest.json`) and
the scripts that fetch it. The dataset copy, task inputs, prompt texts, expert
deliverables, rubrics, and pre-staged web resources are not tracked. Requirements: `uv`
(0.12 was used), Python 3.11, and network access to huggingface.co; no credentials.

```
uv sync --frozen
.venv/bin/python scripts/fetch_dataset.py --revision-file data/dataset_revision.json \
    --out data/gdpval.parquet
.venv/bin/python scripts/resolve_tasks.py --parquet data/gdpval.parquet \
    --out data/selected_tasks.json \
    --deep b5d2e6f1 f841ddcf 47ef842d 1137e2bb c3525d4d \
    --supplementary 7b08cd4d 7d7fc9a7 2ea2e5b5 c357f0e2 a45bc83b
.venv/bin/python scripts/download_materials.py --parquet data/gdpval.parquet \
    --tasks data/selected_tasks.json --revision-file data/dataset_revision.json \
    --log data/download_verification.json
```

Step 2 downloads the parquet at the recorded dataset revision and stops if its SHA-256
differs from the recorded value. Step 3 resolves the ten task ids. Step 4 downloads the
task inputs to `data/inputs/<task_id>/` and the expert deliverables to
`private/gold/<task_id>/`, writes the rubrics to `private/rubric/<task_id>.json` and the
prompt texts to `data/prompts/<task_id>.txt`, and verifies every downloaded file against
the hash Hugging Face records at that revision. On 2026-10-30 this sequence was run in an
empty directory with fresh package and Hugging Face caches; it reproduced
`data/selected_tasks.json` and the ten prompt texts byte for byte.

Optional steps. `scripts/fetch_gcp_resources.py --parquet data/gdpval.parquet --task-id
a45bc83b-22f9-4def-8d89-9c5661b2b86f` re-fetches the public Google Cloud pages and icon
packs used by the design task (about 23 MB); live pages change, so the hashes in
`data/manifest.json` identify the 2026-10-29 fetch rather than a reproducible download.
`scripts/build_manifest.py` rebuilds the manifest from the records.
`scripts/recalc/run_all.py` runs the independent recalculations (needs the inputs and,
for the comparisons with expert deliverables, `private/gold/`);
`scripts/recalc/test_7d7fc9a7_quantization.py` runs the quantization regression checks.

## Sandbox image

The model under test runs in a locally built Docker image (`docker/sandbox/Dockerfile`,
`docker/sandbox/requirements.txt`). The harness refers to that image by its **full local
image ID** (`sha256:<64 hex>`), never by tag: `harness/compose.yaml` (`image:`),
`config.json` (`sandbox.image_id`) and the trusted LibreOffice conversion path in
`grading/extract.py` must all carry the same ID, and the launcher pre-flight refuses to
start when they differ, when the daemon does not know the ID, or when the image platform
differs from `sandbox.platform`. The tag `gdpval-sandbox:stage2` is informational only
(the local daemon has answered tag lookups with "No such image" while the tag was listed).

To rebuild and re-pin:

```
docker build -f docker/sandbox/Dockerfile -t gdpval-sandbox:stage2 docker/sandbox   # on a host whose platform matches sandbox.platform
docker image inspect gdpval-sandbox:stage2 --format '{{.Id}}'      # -> sha256:<64 hex>
```

Write that ID into `harness/compose.yaml` (`image:`) and `config.json`
(`sandbox.image_id`, `sandbox.image`), recompute `sandbox.compose_sha256` as the SHA-256 of
the compose file, and run the launcher `--dry-run` pre-flight. A local image ID identifies
the image content on this daemon only; it is not resolvable on another machine until the
image is pushed or exported, so the cross-machine reference (`sandbox.image_digest`) is
pinned at freeze.
